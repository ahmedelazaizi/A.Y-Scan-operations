# برومت تسليم العمل لعامل التنفيذ (Agent)

انسخ النص التالي كما هو في جلسة جديدة على نفس المستودع والفرع.

---

أنت تكمل بناء **A.Y Scan**: نظام عربي (RTL) لإدارة معمل تحاليل ومركز أشعة، يعمل على Windows بمثبّت Inno Setup وقاعدة PostgreSQL. المالك اسمه أحمد، **كلّمه بالعربية دائمًا**.

## الفرع والحالة
- المستودع `ahmedelazaizi/a.y-scan-operations`، الفرع `claude/eager-gauss-bh88zw` (الـ PR رقم 1 مفتوح عليه، لا تفتح PR جديدًا إلا بطلب).
- ابدأ بقراءة: `docs/WORKFLOW_PLAN.md` (الخطة والقرارات، المصدر الأساسي)، `docs/PRD.md`، `docs/ARCHITECTURE.md`، `README.md`، `docs/devices/`.
- مرجع الشاشات: خريطة الشاشات داخل `WORKFLOW_PLAN.md` (مأخوذة من صور نظام مماثل؛ نقتبس الوظائف والترتيب فقط، والهوية البصرية هوية A.Y Scan في `docs/BRAND_GUIDELINES.md`).
- بيانات جاهزة: `db/seed/price-list-2023.json` (681 خدمة: 368 تحليل و313 أشعة، مع قائمة `review` للصفوف المشكوك فيها)، و`db/seed/reference-ranges-proposed.json` (126 معدلًا مقترحًا بحالة `proposed`). مولّداها في `tools/`.

## المشكلة التي نحلها
الشاشات الحالية CRUD منفصلة (عينة بإدخال رقم الطلب يدويًا، نتيجة بإدخال `orderItemId` والوحدة والمعدل والعلامة يدويًا، فاتورة منفصلة، أشعة منفصلة). المطلوب مسار واحد حول **الطلب**: حفظه ينشئ في معاملة واحدة الفاتورة والعينات بباركود وعمولة الطبيب وتغطية التأمين، ثم يتحرك الطلب عبر: دفع ← سحب ← استلام ← نتائج ← مراجعة واعتماد ← تقرير.

## القرارات المثبتة (لا تعيد مناقشتها)
1. **الدفع شرط قبل السحب:** لا يُؤكَّد سحب عينة إلا بعد سداد الفاتورة كاملة أو تغطيتها بتأمين. الخصم والتأمين يُحددان وقت الطلب. الاستثناء بصلاحية مدير فقط ويُسجَّل في سجل التدقيق.
2. **الاعتماد بشخص آخر:** من أدخل النتيجة لا يعتمدها؛ يفرضه الخادم لا الواجهة.
3. **التسعير:** `contract_price` للقراءة فقط (مرجع الاستيراد)، و`price` تقرره الإدارة وهو ما يراه الكاشير. تعديله بصلاحية، مع سجل أسعار، وأداة تعديل جماعي بنسبة % بمعاينة. الفواتير القديمة تحفظ سعر وقتها.
4. **المعدلات الطبيعية:** تُستورد بحالة `proposed`، ويعتمدها استشاري المعمل **داخل النظام** بدور جديد `lab_consultant` وصلاحية `ranges.approve` (المسؤول لا يعتمد عنه). العلامة التلقائية (طبيعي/منخفض/مرتفع/حرج) تُحسب من معدل معتمد فقط، وبدونه تظهر «لا يوجد معدل معتمد». نص المعدل يُنسخ داخل النتيجة وقت الإدخال.
5. **نموذج البيانات:** الخدمة لها سعر، ولها معاملات (parameters) لكل منها وحدة ومعدلات حسب الجنس والعمر (مثال: صورة الدم الكاملة = Hb وWBC وPLT…).
6. **الأجهزة:** ابنِ الشاشة وسجل الرسائل الخام ومطابقتها بباركود العينة (HL7/ASTM) ومحاكاة. لا تدّعِ ربطًا حقيقيًا بأي جهاز قبل رسائل فعلية منه (انظر `docs/devices`).
7. المدفوعات والمبالغ بالقروش (أعداد صحيحة). المنطقة الزمنية `Africa/Cairo`. تسجيل الدخول باسم مستخدم بسيط، وحساب المسؤول الافتراضي `admin/admin123` يُغيَّر من داخل التطبيق.

## المراحل (انفّذ مرحلة واحدة ثم توقف وانتظر موافقة أحمد)
1. **النواة:** migrations (ترقيم بعد 012): توسيع الدليل (نوع lab/radiology، قسم، اسم إنجليزي، `contract_price`/`price`، أنبوبة)، المعاملات والمعدلات وحالاتها، الباقات، الأطباء والعمولات، إعدادات المعمل (هوية، ترخيص، عملة، ذيل التقرير، شعار/ختم/توقيع)، استيراد الأسعار والمعدلات المقترحة. شاشات: الإعدادات، الأطباء، الباقات، الدليل (مع سجل الأسعار وأداة النسبة)، المعدلات (مع اعتماد الاستشاري).
2. **الاستقبال:** «طلب جديد» بثلاثة أعمدة (مريض/طبيب/أولوية/صيام/تشخيص ← فحوص وباقات ← إجمالي/خصم/تأمين/دفع)، الحفظ الذري للطلب+الفاتورة+العينات+العمولة، كشف الطلبات والفواتير (تحصيل المتبقي)، فاتورة كاشير حرارية بباركود.
3. **العينات:** عينة لكل أنبوبة/فحص، **بوابة الدفع**، تأكيد السحب، رفض بسبب، استلام، ملصق باركود.
4. **النتائج والتقرير:** شبكة إدخال بالطلب، علامة تلقائية من المعدل المعتمد، مراجعة واعتماد بمستخدم آخر، إصدار، تعديل بنسخة جديدة، تقرير A4 (هوية المعمل، سن/جنس، طبيب، نتائج بعلامة، توقيع استشاري وفني، ختم، QR وصفحة تحقق).
5. **الأشعة:** فحوص الأشعة من نفس الدليل والطلب والفاتورة: موعد ← تنفيذ ← تقرير ← اعتماد ← طباعة. الرسوم الإضافية (ملاحظات قائمة الأسعار) رسوم لا خدمات.
6. **الحسابات والمخزون والتقارير:** خزينة وبنك، مصروفات، أرباح وخسائر، ذمم، صرف العمولات، مخزون (حد أمان وصلاحية وصرف تلقائي)، موردون، لوحة تحكم بثمانية مؤشرات ورسوم.
7. **التأمين والزيارات والأجهزة:** خصم الشركة وCo-Pay وموافقة مسبقة وقت الطلب، الزيارة المنزلية تنشئ طلبًا، سجل الأجهزة ومطابقتها بالباركود.
8. **القشرة:** شريط علوي، تبويبات، اختصارات F1–F7، حالات تحميل/خطأ/فارغ، تلميع.

## قواعد العمل (إلزامية)
- كل مرحلة: خطة قصيرة ← تنفيذ ← **`npx tsc -b` و`pnpm lint` و`pnpm test`** (ومعهم `pnpm server:build`) ← إصلاح كل الأخطاء ← تجربة تشغيل فعلية ← commit ← push على نفس الفرع ← تقرير بالعربية ثم **توقف وانتظر موافقة أحمد** قبل التالية.
- لا تُعلن اكتمال شيء لم تشغّله. قل صراحة ما لم تجرّبه (خصوصًا ما يخص Windows وInno Setup فلا بيئة لهما هنا).
- حد أقصى 5 ملفات لكل خطوة متماسكة؛ لما تتجاوز، قسّم أو استخدم sub-agents (5–8 ملفات لكل واحد). أعد قراءة أي ملف قبل تعديله، وتحقق بعد التعديل.
- قبل أي إعادة هيكلة لملف يتجاوز 300 سطر: نظّف الكود الميت وأرسله في commit مستقل.
- لا تكسر المثبّت: ملفات `installer/` وسلوك `setup-database` والقاعدة المدمجة تبقى تعمل. مسار التثبيت ASCII فقط. migrations إضافية فقط (لا تعدّل migration مطبّقة)، والبيانات الحالية للعميل لا تضيع.
- الأمان: لا أسرار في المستودع، كل API بصلاحية (deny-by-default) وaudit للأحداث الحساسة، الخادم يفرض القواعد (الدفع قبل السحب، فصل المُدخل عن المعتمِد، اعتماد المعدلات).
- الاختبارات التكاملية: `service postgresql start` ثم `TEST_DATABASE_URL=postgresql://ayscan_dev:devpass@127.0.0.1:5432/ayscan_dev pnpm test`.
- لا تذكر أي معرّف نموذج في الـ commits أو الكود. لا تُنشئ PR إلا بطلب.

ابدأ بقراءة الملفات المذكورة، ثم اعرض على أحمد خطة المرحلة 1 التفصيلية (الجداول والملفات) وانتظر موافقته قبل الكتابة.
